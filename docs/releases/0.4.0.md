# Termux Muscle 0.4.0

This version moves the default Claude Code pin from **2.1.270** to **2.1.283** and documents **Opus 5.5**.

Opus 5.5 (`claude-opus-5-5`) is documented upstream as requiring client **2.1.280 or later**. The 2.1.270 pin is below that minimum, so a default installation could not select the model; the release gate also rejects a manifest whose documented models require a newer client than the pinned one. Moving the pin to 2.1.283 resolves both.

| Pinned payload | 0.3.2 | 0.4.0 |
| --- | --- | --- |
| Claude Code | 2.1.270 | 2.1.283 |
| musl loader | 1.2.6-r2 | 1.2.6-r2 |

The recorded source identity for 2.1.283 is Anthropic's official ARM64 musl package, unmodified:

## Not publishable yet: device acceptance is outstanding

`compatibility.json` registers **no** device report and omits `verified_on`, so `tm-core release-check` refuses this version and `scripts/build_release.sh --release` cannot produce assets. That is the intended state until acceptance exists. A development build (`bash scripts/build_release.sh --output dist`) works and its generated notes state plainly that no device acceptance is asserted.

Acceptance **cannot** be produced from inside an already-running managed Claude Code session. The runtime writes a namespace sentinel at `/.termux-muscle-namespace.json` inside its PRoot environment, and `nested_release()` rejects starting a candidate whose installation identity does not match it:

```
termux-muscle: runtime_nested_conflict: A different installation owns this namespace; start a fresh Termux shell.
```

That guard is correct and must not be worked around. It means the candidate startup checks (`startup_version`, `startup_help`, `startup_init`) fail with `probe_failed` when acceptance is attempted from within a managed session, even though acquisition and integrity verification succeed.

Run maintainer acceptance from a **fresh native Termux shell that is not inside Claude Code**:

```sh
cd path/to/termux-muscle
scripts/maintainer_acceptance.sh --preflight                 # checks only; changes nothing
scripts/maintainer_acceptance.sh --model claude-opus-5-5     # full run; one real model request
```

The script builds the helper, then runs source bootstrap (`--no-link`), the isolated startup checks, an offline update, an authenticated Bash-tool check, an offline rollback and uninstall, all inside a disposable data root and HOME. It fingerprints the live installation's commands, manual, completion and state before and after, and exits 3 if anything changed. Each required check is PASS only when its own outcome was observed. The tool check requires a real Bash tool call on the fixture, a matching successful tool result, an attestation file written by the fixture itself, and a successful final result. The model check requires every reply to come from exactly the requested model. The script then evaluates the report with the real release gate in a scratch copy and prints the verdict, without registering the report.

Without `--model`, no model request is made, `shell_tools` stays SKIP, and the report cannot pass the gate. With it, the request uses your normal Claude credentials, bounded by `--max-budget-usd 0.50`; user settings, hooks, MCP servers, skills and session persistence are disabled for that run.

Registering the report remains a reviewed step: rename it to the device-and-date convention, write its notes, set `verified_on` and `reports` in `compatibility.json`, and rerun `build/tm-core release-check .`.

## Updating an existing installation before 0.4.0 is published

From a fresh Termux shell, an existing installation can take the new pin directly from a checkout without waiting for a published manager release:

```sh
cd path/to/termux-muscle && make && ./bin/termux-muscle update
```

Either way the candidate must pass its startup checks before activation, and `termux-muscle rollback` restores the previous local release without a download.
