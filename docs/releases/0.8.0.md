# Termux Muscle 0.8.0

This version moves the default Claude Code pin from **2.1.283** to **2.1.284** and documents **Sonnet 5.5**.

Sonnet 5.5 (`claude-sonnet-5-5`) is documented upstream as requiring client **2.1.284 or later**. The 2.1.283 pin is below that minimum, so a default installation could not select the model; the release gate also rejects a manifest whose documented models require a newer client than the pinned one. Moving the pin to 2.1.284 resolves both. The 2.1.284 executable contains the `claude-sonnet-5-5` identifier; the 2.1.283 executable does not.

| Pinned payload | 0.7.0 | 0.8.0 |
| --- | --- | --- |
| Claude Code | 2.1.283 | 2.1.284 |
| musl loader | 1.2.6-r2 | 1.2.6-r2 |

Both digests were confirmed three ways: the registry metadata for 2.1.284 reports the same integrity value; a real acquisition run on a Galaxy S26 Ultra (`termux-muscle update --claude-version 2.1.284 --allow-unverified` under 0.7.0) downloaded the archive, matched the integrity value, extracted the payload and recorded this executable SHA-256 before its startup checks passed; and extracting the verified cached archive again reproduced the same executable digest. The upstream release tracker opened the corresponding compatibility-testing issue on 2026-09-28.

Checked **2026-09-29** against [Anthropic's model configuration documentation](https://code.claude.com/docs/en/model-config), which states that Sonnet 5.5 requires Claude Code 2.1.284 or later and Opus 5.5 requires 2.1.280 or later. **No model is verified for 0.8.0 until its device acceptance is registered.** The Opus 5.5 results for 0.4.0 through 0.7.0 on the 2.1.283 pin, the Sonnet 5 results for 0.2.0 through 0.3.2, and the Opus 5 and mixed Fable observations in 0.1.0 remain dated evidence for those releases and are not relabeled here.

A community `termux-muscle test --model claude-fable-5-1` run on 2026-09-29 against the live 2.1.284 installation recorded `model_fallback_observed`: responses came from both `claude-fable-5-1` and `claude-opus-5`. That is an upstream availability or fallback outcome, not a Termux Muscle check, and it is why Fable 5.1 is not proposed as the acceptance model.

## Device evidence

Acceptance for 0.8.0 has not been registered yet. Produce it with `scripts/maintainer_acceptance.sh` from a **fresh native Termux shell that is not inside Claude Code**, in a clean checkout of the commit that moves the pin:

```sh
make check
scripts/maintainer_acceptance.sh --model claude-opus-5-5
```

Inside a managed Claude Code session, the runtime's nested-namespace guard refuses to start a candidate release (`runtime_nested_conflict`), so the script refuses to run there and explains why. It also refuses a checkout with uncommitted or untracked files, because such evidence would describe no commit.

## Updating an existing installation

From a fresh Termux shell, update the manager, then the runtime:

```sh
termux-muscle self-update
termux-muscle update
```

A 0.7.0 manager's `update` uses its own 2.1.283 pin, so run `self-update` first. An installation that already runs 2.1.284 through `--allow-unverified` keeps working; after `self-update`, `termux-muscle versions` reports that release as pinned, and `update` is a no-op for the runtime. Either way a candidate must pass its startup checks before activation, and `termux-muscle rollback` restores the previous local release without a download.
